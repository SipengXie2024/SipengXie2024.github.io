LLM Inference Infra / Tutorial by Worked Example

先量，再改

这是一篇教程。它用一次真实的 DeepSeek-V4.1 推理优化，带你走一遍"量、归类、估上限、探针、验收"五步。 两处 kernel 改动只是例子；文中猜错的预测和走过的弯路，和最后的答案一样值得看。

环境：8 × RTX PRO 6000 Blackwell Server Edition（SM120，GDDR7，PCIe 5.0，无 NVLink），vLLM 社区 fork yhfgyyf/vllm-deepseek-v4-sm89， TP8 + 专家并行，DSpark 投机解码 k=5，max-model-len 1,048,576。所有数字都在关闭对外流量后、用同一套脚本测得。 每个关键数字出现前有一道估算题，先自己算，再点开看答案。

01

第一步：先量，时间花在哪

动 kernel 之前，先拿一份端到端的 trace，把时间按类别拆开。

先交代对象。DeepSeek-V4.1 的稀疏注意力不对全部 key 做注意力：一个轻量的索引器先给每个 query 行和缓存里的每个 key 打分 （32 个头 × 128 维的点积，再按头加权求和），挑出分数最高的 512 个 key，真正的注意力只在这 512 个上做。 索引器的 q 和 K 缓存都是 MXFP4：每个数 4 比特（e2m1，只有 0、±0.5、±1、±1.5、±2、±3、±4、±6 十六种）， 每 32 个数共用一个 8 比特的 2 的幂次倍率。

我们用 torch profiler 抓了一条 200k token 冷启动预填充的 trace（25 块 × 8188 token），取 rank 0，把 kernel 时间按名字归类：

类别GPU 时间占比
NCCL all-reduce5.43 s40%
索引器打分 kernel4.31 s32%
MoE（Marlin、mxfp8 GEMM、SwiGLU）约 1.5 s11%
注意力0.97 s7%
norm 及其他约 1.3 s10%

只看这张表，最大的是 all-reduce。但我们要的是 100 万 token，所以还要看每一项怎么随长度变化。 按块拆开：all-reduce 每块都是 222 ms 左右，和已有上下文无关；索引器第 1 块 13.0 ms、第 10 块 139 ms、第 20 块 279 ms，随块号线性增长。

100 万 token 是 128 块。索引器总共要多少秒？

第 k 块约 13 ms × k，总和是 13 ms × (1 + 2 + … + 128) = 13 ms × 128 × 129 / 2 ≈ 107 s。

all-reduce 只是 128 × 222 ms ≈ 28 s。200k 时它是第一名，到 1M 时索引器反超成大头：总量是平方增长对线性增长。

按你关心的工作点排序，不按某一次 trace 的占比排序。

数字对不上

现象
一份早期调研报告说索引器在这条 trace 里占 6.46 s，我用同一个脚本重算只有 4.31 s。
原因
报告引用的是前一天另一条 trace，那时跑的是更早一版索引器 kernel（启动网格列数差 8 倍）。两个数都对，只是来自不同的程序版本。
下一步
之后每个数字都带上来源：哪个版本、哪条 trace、哪个脚本。所有派生的推算从对上的那个数重新算。
02

第二步：归类，它是哪一种瓶颈

Horace He 在 Making Deep Learning Go Brrrr From First Principles 里把慢分成三类：算力（compute）、搬数据（memory）、额外开销（overhead）。类别决定了该怎么改。

overhead

生成阶段的索引器

生成阶段用 CUDA Graph 重放整步，kernel 的启动网格按最大上下文录死。宽度 512k 时，上下文 2k、200k、满宽三种情况分别是 287、310、357 µs：有效工作差了 256 倍，时间几乎不变。时间不跟着有效工作走，就是 overhead 的特征。

compute，用错了单元

索引器里的 FP4 解码

原算子先在普通 CUDA 核上把 4 比特翻译成浮点：每个 16 列的块要翻译 2048 个 K 值，每个十几条整数指令。 而矩阵乘只有 32 行（32 个头），张量核心几微秒就算完。时间花在翻译上，张量核心在等。

memory

生成阶段的 MoE

每步 86 次 Marlin 调用，合计 1.9 ms；每张卡每步要读的专家权重约 3.4 GB（43 层 × 约 4.5 个本卡命中的专家 × 17.7 MB）。

宽度 1M、上下文 2k 时，网格里有多少个 16 列的块？有 key 的有几个？

220 / 16 = 65,536 个块；有 key 的只有 2048 / 16 = 128 个，占 0.2%。

剩下的 6 万多个块到岗后写一个 -inf 就走，但派出一个块本身要调度、要装载 q 向量。实测这一次调用 574 µs，有用的计算不到 1 µs，每步 8 次。

MoE 每步读 3.4 GB、用 1.9 ms，折合多少带宽？这张卡的显存峰值是多少？

3.4 GB / 1.9 ms ≈ 1.79 TB/s。RTX PRO 6000 Blackwell 是 GDDR7，峰值 1.79 TB/s。

已经贴着带宽上限。换成更快的计算 kernel 也省不掉读权重的时间，所以单路生成时不值得给 MoE 换算子。

先判断类别再动手：overhead 要减少无用的启动，compute 要换到更快的单元，memory 要少读字节。三类的解法不能互换。

03

第三步：估上限，改完最多快多少

动手之前写下预测。预测对了说明你理解了系统，错了说明还有没建模的部分。

Amdahl 定律：某部分占总时间的比例是 f，它快了 s 倍，总时间变成原来的

T新 / T旧 = 1 − f + f / s

要两个数：s 是算子自身快了几倍，f 是改动前它的绝对耗时占端到端时间的比例。改动二让 200k 预填充的索引器块从 23.7 ms 变成 1.77 ms，s = 13.4。

用第一步表里的 32% 当 f，200k 冷启动 TTFT 应该变成原来的多少？实测是 14.2–15.9 s → 11.3–12.5 s，对得上吗？

1 − 0.32 + 0.32 / 13.4 ≈ 0.70。实测取区间中点，15.05 s → 11.90 s，比值 0.79。对不上。

问题在分母。32% 是索引器占 GPU 时间的比例，而 TTFT 里还有 GPU 空闲的时间（CPU 准备每块输入、调度）。f 必须是它占你要优化的那个指标的比例。

索引器每个 200k 请求约 3.5 s（由更早一版 kernel 的 trace 按基准倍数折算，是估算），占换前 TTFT 15.05 s 的 23%。 代进去：1 − 0.23 + 0.23 / 13.4 ≈ 0.785，预测 TTFT 约 11.8 s，实测 11.3–12.5 s。对上了。

f 的正确量法：从当前版本的 trace 里把这个算子每个请求的绝对耗时加起来（秒，不是百分比），除以客户端测到的端到端时间。两个数必须来自同一个程序版本。我们这里的 3.5 s 是折算的，因为手头的 trace 来自更早一版 kernel。

1M token 冷启动从 135 s 降到 61 s，算子快了 12–13 倍。反推索引器原来占多少？

61 / 135 = 0.452 = 1 − f + f / 12，解得 f ≈ 0.6，即约 80 s。

和第一步按块外推的量级一致：长上下文下，索引器超过一半。

1M 的预测猜错了 35%

预测
改动前，我按 200k 的 profile 外推 1M 冷启动约 100 s。
实测
135 s，低估了 35%。说明除了索引器和 all-reduce，还有别的部分随长度超线性增长。
改动后
按每块 222 ms all-reduce 加约 150 ms 其他部分线性外推，128 块应是 47.6 s，实测 61 s，仍有约 13 s 没有归因。
现状
后来找到其中约 2 s（估算）：每块一次阻塞的 device→host 拷贝让 CPU 串行等 GPU。其余的还没解释，列为下一个 profile 的目标。

估上限也用来决定不做什么。我们本来计划把索引器按行分摊到 8 张卡（代码写好了，2 卡测过结果一致、快 1.9 倍）， 但改动二之后，按同样的算法估，它在 1M 时最多再省约 6 s（61 s 里），在 200k 只省 1–2%，还要多加几百次跨卡通信，所以没上线。 第二步里 MoE 的上限是零，也没做。

写下预测再测。预测对了就继续，错了就把差值留着当线索，不要把它抹平。

04

对症：overhead 型，让固定数量的人干可变的活

CUDA Graph 不许改派人数，那就固定人数，让每个人干的活跟着上下文变。

为什么不能直接 return

空块照样要调度

"越界就 return"省不掉几万个空块的调度开销。而且图里的网格不能随上下文变，上下文每步都在涨，不能每步重新录图。

类比

线程池

工作线程数固定，任务数可变，每个线程循环着从任务里取。CUDA 里这个写法叫 grid-stride loop。 通常用它是为了控制并行度，这里用它是因为录好的图不能改派人数。

做法

循环上限在重放时读

网格改成"行数 × 每行固定数量的 program"，第 i 个 program 处理第 i、i+N、i+2N…… 块，循环到这一行的真实末尾 （row_ends，重放时才读）就停。越界的列由一个很便宜的填充循环写 -inf，输出和原来逐位一致，下游代码不用改。

grid-stride loop · row_ends read at replay time
row = tl.program_id(0)
first = tl.program_id(1)
stride = tl.num_programs(1)
# this row's real context, read at replay time
stop = tl.minimum(tl.load(row_ends + row), width)
last = (stop + BLOCK_N - 1) // BLOCK_N
n = (last - first + stride - 1) // stride
for i in range(0, n):          # constant-step loop
    tile = first + i * stride
    ...score BLOCK_N keys, store...
# [last*BLOCK_N, width): -inf fill loop

第一版满宽度反而变慢

第一版
每行固定 1024 个 program（扫过 512 到 4096）。短上下文快了几十倍，但满宽度慢 10%，预填充慢 13%。
假设
预填充一次有几百到几千行，每行 1024 个 program，总数太多：每个 program 只处理几块，却都要装载一遍 q；处理同一列块的各行也分散在不同时间，K 块没法在 L2 里共用。
改法
让 program 总数固定在一万六左右：每行 min(列块数, max(8, 16384 / 行数)) 个。行少（生成阶段）时每行多开，换并行度；行多（预填充）时每行少开，q 只装一次，K 块在 L2 里被各行共用。同时把循环改成常数步长。16384 是在 16384、65536、262144 三档里扫出来的，下限 8 是经验值；换一块卡或换一个 kernel 要重扫。
结果
满宽度持平，预填充慢 2–3%（可接受），候选块路径快 6%。两处是一起改的，没有分开测各自的贡献。
算子级（1 条请求，4 行）改动前改动后
宽度 512k，上下文 2k287 µs19 µs
宽度 512k，上下文 200k310 µs144 µs
宽度 1M，上下文 2k574 µs19 µs
4 条请求，上下文 2k1119 µs25 µs
满宽度357 µs357 µs

系统级：短上下文生成 +18%，150k 上下文 +22%，200k 冷启动 TTFT −6%。满宽度持平，说明改动只去掉了扑空的部分，没碰有用的计算。

overhead 的判据是"时间不随有效工作变化"；改完之后，时间应该开始随有效工作变化。

05

第四步：先写探针，确认硬件路径走通，再换指令

Blackwell 的张量核心能直接读 MXFP4。在押上整个 kernel 之前，先花十分钟确认编译器真的用上了它。

类比

请一个会读原文的会计

原来是请翻译把每页外文念成中文，再让会计算账，会计大部分时间在等翻译。 现在换一个懂外文的会计，直接拿原件算。翻译这一步整个消失。

指令

tl.dot_scaled

Blackwell 新增了块缩放 FP4 矩阵乘指令 mma.sync.m16n8k64.kind::mxf4nvf4.block_scale， 直接吃 4 比特字节和 8 比特倍率。Triton 3.7 把它封装成 tl.dot_scaled。

陷阱

软件回退

在没有原生支持的硬件上，Triton 会把 FP4 先升成 bf16 再乘。代码照样能跑、结果照样对，只是不快。 不先确认，你可能在一个假的加速上搭完整个 kernel。

探针是一个只做一次 32 × 16 小矩阵乘的 kernel。编译后在 PTX 里找指令名，同时和原算子逐位比较：

probe: did it lower to the native instruction?
h = probe_dot_scaled[(1,)](q_bytes, q_scales, k_bytes, k_scales, out, N=16)
mmas = set(re.findall(r"mma\.sync\.aligned\.[\w.:]+", h.asm["ptx"]))
# SM120: {'...kind::mxf4nvf4.block_scale...e2m1.e2m1.f32.ue8m0'}
# empty set -> software fallback; stop here
assert torch.equal(out, decode_then_bf16_dot(...))   # same 16 columns

探针通过后才改正式 kernel：把"装载 → 翻译 → bf16 点积"换成"装载 → dot_scaled"，q 的预解码 kernel 也一起省掉。 上线前还在生产的编译参数下（同一个 ptxas）重跑了一遍，结果和耗时不变；上线后又在生产的 Triton 缓存里确认了 PTX 里有这条指令。

K stays packed · scales as [N, K/32]
# K stays packed: [64 bytes, N] e2m1 pairs
k_bytes = tl.load(k_cache + v_off,
                  mask=valid[None, :], other=0)
# ue8m0 scales as [N, K/32]
k_scales = tl.load(k_cache + s_off,
                   mask=valid[:, None], other=127)
scores = tl.dot_scaled(q_bytes, q_scales, "e2m1",
                       k_bytes, k_scales, "e2m1")
# fp32 [32 heads, N]; no decode anywhere

翻译没了之后，每块的列数不再受翻译成本限制，原来的 16 列是迁就翻译的。扫了 16 / 32 / 64 / 128 列 × 1–3 级流水 × 4 / 8 warp， 128 列、1 级流水、4 warp 最好。

为什么总倍数（预填充 13 倍）比"去掉翻译"本身还高？

每块都有固定开销：算地址、读页表、读倍率。列宽从 16 变到 128，同样的固定开销摊到 8 倍的列上。去掉翻译是一部分收益，摊薄固定开销是另一部分。

算子级（空闲 GPU）改动前改动后倍数
生成，上下文 2k18.6 µs12.4 µs1.5
生成，上下文 200k144 µs21 µs6.9
生成，1M 满宽701 µs63 µs11.2

用新指令或新 API 之前，先写一个最小探针看编译产物。能跑、结果对，不等于走了你以为的硬件路径。

06

第五步：验收，怎么证明没改坏

验收标准从严到宽排成一架梯子，能站在高一级就不下到低一级。

  1. 01

    逐位一致

    改动一做到了：基准里的 13 种形状上，整个输出缓冲区（包括写 -inf 的越界列、包括 CUDA Graph 重放）和原算子逐位相同。能做到就不需要讨论精度。

  2. 02

    说清差异从哪来，并证明下游用到的量不变

    改动二做不到逐位一致。原因可以说清：4 比特的数乘 2 的幂在浮点里都能精确表示，每个乘积是精确的，差别只在张量核心内部累加 128 个乘积的顺序， 最大相对差 1.7e-7（fp32 的最后一位）。下游只用分数排序挑前 512 个，所以验收看 top-512 集合： 11 种生产形状上，和原算子、和 fp64 参考完全一致。

  3. 03

    端到端精度门

    同一份权重、同一协议前后各跑一次：GSM8K 1277 / HumanEval 157 / MMLU 11873，对比改动前 1277 / 157 / 11877； 配对检验 p = 1.0 / 1.0 / 0.85。这些数只说明前后持平，不是官方模型的成绩。

  4. 04

    先确认指标的分辨率

    精度门有一项分辨率不够，见下面的估算题。

HumanEval 有 164 题。一题是多少个百分点？同一配置什么都不改，重复跑的结果在 153–159 之间，单跑一次能判断 ±1 个百分点吗？

一题 = 100 / 164 ≈ 0.61 个百分点；153–159 相当于 3.7 个百分点的离散。单次结果判不出 ±1 个百分点。

我们改动前后各单独跑 10 次取均值：156.6 → 156.2。离散的来源是 T=0 下批次组成不同带来的数值差异（同一题两次从第一个字符就分叉），和 kernel 无关。

测速也要先检查指标本身。投机解码每次的接受率不同，tok/s 会把"草稿猜得准不准"混进"kernel 快不快"里。 比较时换算成每步耗时：每步产出 token 数 = 1 + 5 × 接受率（k = 5），每步耗时 = 每步 token 数 / tok/s。

1M 场景改动前 334.9 tok/s（接受率 0.64），改动后 353.8 tok/s（接受率 0.56）。看 tok/s 快了 6%，每步实际快了多少？

改动前每步 4.20 个 token，4.20 / 334.9 ≈ 12.6 ms；改动后每步 3.80 个，3.80 / 353.8 ≈ 10.8 ms。

每步快了约 15%。tok/s 只显示 6%，因为改动后那次运行的草稿接受率碰巧更低。

验收前先问：这个指标能分辨我要的差异吗？它有没有混进和改动无关的变量？

07

别被工具骗：profiler 造出来的瓶颈

改完索引器后，我们想看离硬件极限还有多远，结果先追了一个不存在的瓶颈。

总有一张卡迟到

现象
带 torch profiler 的 8 卡 trace 里，200k 上下文每步生成 19.8 ms。总有一张卡的 GPU 空转约 30%，其余七张在集合通信里等它。看起来像 CPU 受限。
假设 1
调度进程和那张卡的 worker 抢 CPU 核。把调度进程绑到别的核：迟到的卡换成了另一张。再把所有进程绑到互不相交的物理核：又换了一张。迟到没有消失，只是换了位置，假设被推翻。
假设 2
NUMA、PCIe 链路、专家负载不均。8 张卡的 kernel 启动数完全相同，非通信 kernel 的时间也相同，8 条链路都是 Gen5 x16。三个假设一起排除。
假设 3
测量工具本身。不带 profiler 时每步只有 12.8 ms，而这套算子的 GPU 下限（迟到那张卡的实际忙时，没有等待）是 11.5–12.7 ms。
结论
生产里每步的 CPU 时间略低于 GPU 时间。profiler 的回调（CUPTI）给每步加了 CPU 开销，把它推过临界点，于是总有一张卡的 CPU 来不及喂 GPU。
GPU 下限
怎么算：取迟到那张卡在 trace 里所有 kernel 的时间区间，求并集长度（重叠只算一次），除以步数。它没有等别人，所以它的忙时就是这套 kernel 的下限。
回头看
顺序反了。应该第一步就比较带和不带 profiler 的每步耗时，我们放到了最后，前两个假设白查了。下面排查表里给的是正确的顺序。

回滚与复现

两处改动都只是替换一个文件。

两处改动都是把替换的 dsv41_indexer.py 挂载进容器覆盖 fork 里的同名文件，回滚只需换回原文件重启。 合并后的版本（SM120 走 dot_scaled，其他架构保留原来的解码路径，两条路径都带 grid-stride 跳过）已提交上游 PR #156，附测试。 算子级基准对比的是公开 wrapper（dsv41_mxfp4_dense_logits / dsv41_mxfp4_candidate_logits）的输出， 改动一按逐位、改动二按 top-512 集合和 fp64 参考比较，在 SM120 机器上可以复现。

数字只代表这套机器和这个 fork。在没有 NVLink 的 PCIe 机器上，改完索引器之后的瓶颈是集合通信； 改动二的倍数在其他架构上取决于是否有原生块缩放 FP4 指令（SM100 有对应的 tcgen05 路径，SM89 没有）。 写法上参考了 Simon Boehm 的 How to Optimize a CUDA Matmul Kernel for cuBLAS-like Performance: a Worklog。
