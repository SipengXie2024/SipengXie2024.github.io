四个 Agent Harness：同一个需求，四种相反的答案

2026 年 8 月 13 日，DeepSeek 开源了自己的 agent harness——dsh（DeepSeek Harness），发布当天 star 数破 1.5 万。 「包在模型外面、让它能替你干活的程序」这个需求，四家做出了形态完全不同的东西。这组笔记基于一手材料——dsh 的仓库源码与架构文档、Pi 和 Codex 的官方仓库、2026 年 3 月泄露的 Claude Code 源码——回答一个问题：它们的分歧到底在哪，又在哪些地方不约而同。

Harness 01 · 平台化

dsh（DeepSeek Harness）：一切皆插件

deepseek-ai/deepseek-harness TypeScript · MIT · Developer Preview

大多数 agent 是「一个程序」；dsh 是「一堆插件在启动时拼出来的程序」。它建立在 vendored 的 Cordis 框架上：模型适配器、工具注册表、会话日志、agent loop 本身都是插件，没有一个可供打补丁的「核心」。

它在解决什么（大白话）

普通 harness 像一套精装房：开发商（Anthropic、OpenAI）替你决定好格局，你只能在软装层面调整——换窗帘（hooks）、添家电（MCP）。dsh 交付的是一套乐高底板：每面墙都是可拆的模块，官方先按图纸（profile）替你拼好一套能住的，但任何一面墙你都可以换成自己的。

组合方式分三层：profile（配置档，声明叠哪些 bundle）→ bundle（插件包，发行格式）→ patch（用户的 YAML 补丁层）。启动时按顺序叠加成一棵插件树，dsh --dump-config 可以看到自己机器实际拼出来的样子，树里任何一行都能被你的 patch 整行替换。官方明说当前是 developer preview，会有破坏性变更。

读完要能复述的核心概念

  • 会话日志是唯一事实来源

    append-only 的 SessionEvent 日志；有一条运行时不变量「model-visible ⟺ logged」——凡进入模型请求的内容必须能从日志重建。fork、resume、transcript、telemetry 全部从日志派生。

  • 能力接缝（capability seam）三角色

    每个可替换能力由 Service Definition（接口）/ Service Provider（实现）/ Consumer（通常是模型工具）三元组构成。换掉 fs/subprocess 的实现，bash、终端、LSP 会一起搬进远程沙箱，无需改任何工具代码。

  • 出厂 30+ 模型工具

    除常规读写改查外，还有 run_code（Code Mode：模型写代码、代码里调工具）、6 个持久终端 PTY 工具、lsp、可持续对话的后台 subagent 全家桶、workflow/ralph（每轮换新子代理的固定循环）、goal_*/schedule_*（长期目标与定时唤醒）、session_query（查自己的历史会话），以及 cordis_*——agent 在运行时检视、挂载、卸载自己的插件。

  • 与现有生态的直接缝合

    llm-pi-ai 包直接依赖 Pi 项目的 pi-ai 库作为多厂商模型后端；packages/hooks 提供 Claude Code hooks 和 Codex hooks 的桥接层；另有 MCP client 与 ACP（Agent Client Protocol）服务端。

关键事实

15k+ star / 发布当天

2026-08-13 创建并开源。约 50 个 workspace 包、TypeScript 严格 ESM、per-file 100% 覆盖率门禁、无密钥快照回放测试、全双语文档、每个非平凡改动强制附带 Agent Note——工程规格在四家中最重。

值得停下来想

这份 AGENTS.md 本身就像一部写给 agent 的操作规程。种种迹象（文档密度、测试纪律、笔记制度）表明这个仓库的开发过程高度 agent 驱动——它可能本身就是 dsh 自己参与开发的。

Harness 02 · 极简

Pi：核心什么都不给，是故意的

badlogic/pi-mono TypeScript · MIT · Mario Zechner

Pi 的回答与其他三家相反：别人往里加，它往外拿。默认只给模型 4 个工具——read、write、edit、bash，其余一概不内置。89k star 说明这条路有相当的市场。

它在解决什么（大白话）

Pi 作者的判断是：子代理、plan mode、权限弹窗这些功能，每个人想要的样子都不一样，harness 替你做的任何决定都是错的决定。所以它给一把锋利的小刀和一套结实的刀架（扩展系统），剩下的你自己造——或者从别人造好的（pi package）里挑。

官方 README 有一份「没有 X 怎么办」清单：没有 MCP？写个扩展接，或者干脆给 CLI 工具配 README（skill）。没有后台 bash？用 tmux，还能直接观察和交互。没有权限弹窗？跑在容器里。没有 todo？用 TODO.md 文件——他们认为内置 todo 会让模型困惑。

读完要能复述的核心概念

  • TypeScript extension 系统

    扩展可以注册自定义工具（或整体替换内置工具）、命令、键盘快捷键、事件处理器、UI 组件——子代理、plan mode、权限门、自定义 compaction 都被官方列为「扩展能做的事」。

  • pi-ai：统一的多厂商模型 API

    30+ 提供商（含 Claude/Codex/Copilot 订阅登录），这份模型抽象好到被 dsh 直接当依赖用（llm-pi-ai）。

  • 树形会话

    会话是一棵可以从任意节点分支的树，自带 compaction；运行模式有四种：interactive、print/JSON、RPC、可嵌入 SDK。

  • 安全靠环境，不靠产品

    Pi 明确不含任何权限系统，默认以启动用户的全部权限运行；需要隔离就容器化（官方文档给出 micro-VM、Docker、策略沙箱三种方案）。

关键事实

4 个默认工具

read / write / edit / bash。作者理由是：默认工具越少，模型行为越可预测，扩展组合出的形态越不受内置决策拖累。

与 dsh 的对照

dsh 和 Pi 都选「可组合」，但路径相反：dsh 靠运行时插件系统 + YAML 组合层（平台化），Pi 靠把核心削到最小（减法）。前者重框架，后者重纪律。

Harness 03 · 一体化

Claude Code：集成产品，配置面扩展

Anthropic · 闭源 分析基于 2026-03 泄露源码（v2.x）

Claude Code 不开源。2026 年 3 月，有人从其 npm 包（打包压缩过的 cli.js）的 source map 还原出完整的 TypeScript 源码，GitHub 上有多个镜像存档。下面的架构描述基于这批泄露代码，细节可能与当前版本有出入。

它在解决什么（大白话）

Claude Code 的思路是消费电子产品：开箱就是完整形态，打磨做到最好，但你只能在它划好的扩展面上活动。

泄露源码里能看到一个单体应用：React Ink 渲染的终端 UI、QueryEngine 驱动的 agent loop、全套内置工具（Bash、文件读写、Glob/Grep、Task 子代理、TodoWrite、WebFetch 等）、权限模式、自动 compaction。扩展面是配置而非代码：hooks、MCP server、slash command、CLAUDE.md、子代理与 skill 定义——能加行为，但换不掉 loop 本身。

读完要能复述的核心概念

  • 内置、打磨、绑模型

    功能范围在四家中最接近 dsh 的出厂集（子代理、todo、计划、web、后台任务都有），但只服务 Anthropic 自己的模型，所有调优都为 Claude 的行为习惯做。

  • 权限系统在产品内

    权限模式 + 细粒度规则（允许/询问/拒绝）是产品的一部分，与 dsh 的审批策略插件、Codex 的 OS 沙箱是三条不同路线。

  • hooks 成了事实标准

    它的 hooks 机制影响大到 dsh 专门写了兼容桥（hooks-claude-code），让为 Claude Code 写的 hooks 可以直接搬进 dsh 用。

关键事实

配置面 扩展方式

hooks / MCP / slash command / CLAUDE.md / skill / 子代理定义。没有代码级插件 API，也没有会话 fork 树。

证据边界

本节是四节中唯一不基于官方开源材料的。泄露版本为 v2.x（2026-03），此后闭源开发仍在继续，最新行为请以官方文档为准。

Harness 04 · 安全优先

Codex：Rust 重写，沙箱是一等公民

openai/codex Rust · Apache · OpenAI

别人先拼功能，Codex 先拼约束：agent 默认跑在操作系统级沙箱里，能碰哪些文件、能不能联网由系统强制，而不是靠模型自觉或产品层的弹窗。

它在解决什么（大白话）

如果把 agent 比作实习医生，Pi 说「让他上大手术台，但整个手术室在玻璃房里」；Claude Code 说「每个动作前护士确认一遍」；Codex 说「先把他能进的房间从门禁系统里限定死」。dsh 则把门禁系统本身做成了可替换模块（landlock 内核模块、Windows ACL、E2B 远程沙箱任选）。

工程上 Codex 是四家里唯一用 Rust 的：核心、终端 UI（ratatui）、非交互 exec 模式、MCP server 分层为独立 crate，发单一静态二进制。产品上与 ChatGPT 订阅、云端 Codex（Web/App）深度绑定，是「本地 CLI + 云端任务」两条腿走路的唯一一家。

读完要能复述的核心概念

  • OS 级沙箱 + 审批策略

    macOS 用 Seatbelt、Linux 用 Landlock/seccomp，审批模式（只读/工作区写/完全放开）决定 agent 的默认边界——安全能力来自操作系统，不来自提示词。

  • 声明式配置

    config.toml + AGENTS.md + profile；MCP 既是 client 也能把自己暴露成 MCP server 被别的 agent 调用。

  • 云端一体化

    同一个 Codex 账号下，本地 CLI、IDE 插件、桌面 App、云端任务共享任务流——harness 的边界从终端延伸到了 OpenAI 的产品矩阵。

关键事实

105k+ star

四家中 star 最高。开源（Apache），但模型面只服务 OpenAI 模型与 ChatGPT 订阅。

值得停下来想

dsh 的 native/ 目录里同样有一个 landlock 的 Node 原生 addon（外加 Windows ACL 沙箱包）——「内核级文件系统隔离」这条由 Codex 趟出来的路，dsh 直接跟进了。

03

四条核心判断

前两条是材料里能核实的事实，后两条是推断——都标了证据边界。

1

事实 · 来自四个仓库的直接阅读

根本分歧是「功能该内置还是该组合」，而不是功能清单

  • 四家都能做出「读文件、跑命令、改代码」这个基础闭环；真正的分野在：超出基础闭环的功能由谁、以什么粒度提供。
  • Claude Code 和 Codex 把 plan、子代理、权限做进产品，换取开箱即用和行为可控；Pi 判定这类决策必然众口难调，于是全部推给扩展；dsh 判定应该让它们可替换而不是不存在——出厂给全套，但每一件都能被 patch 换掉。
  • dsh 与 Pi 都选「组合」，代价结构不同：dsh 用户要理解 Cordis 的插件/事件/effect 心智模型（学习成本前置），Pi 用户要自己动手造轮子（工程成本后置）。
为什么重要

选型时不该比功能清单（都会趋同），而该问：这个 harness 的哪个决定是我改不掉的，我能不能接受。

2

事实 · 代码级证据

dsh 与另外三家都有直接的代码级关系，策略是做兼容层

  • packages/llm/llm-pi-ai：直接把 Pi 的 pi-ai 库作为多厂商模型后端打包进 dsh——Pi 的模型抽象好到被竞品当依赖用。
  • packages/hooks：Claude Code hooks 与 Codex hooks 的桥接实现 + wire-protocol 库——为那两家写的 hooks 配置可以搬进 dsh。
  • 协议面同样铺全：MCP client、ACP（Zed 的 Agent Client Protocol）服务端、自有 JSON-RPC SDK 与 Python SDK。
为什么重要

这是在降低整个生态的迁移成本：用户为别家积累的 hooks、MCP server、模型配置，在 dsh 里都不是沉没成本。作为后来者，这是合理的进攻姿态。

3

推断 · 有间接证据，无官方证实

dsh 很可能是 DeepSeek 内部训练/评测的配套 harness

  • 间接证据：DeepSeek 模型适配器是一方包；e2e 测试直接打真实 API；工具 schema 的打磨粒度远超一般开源项目；还专门留了跑 benchmark 的说明（Python SDK + headless 模式）。
  • 如果这个猜测成立，那么 DeepSeek 的模型很可能就是对着这套工具 schema 和 agent loop 做过后训练——那么 dsh + DeepSeek 模型的组合，契合度会高于任何第三方 harness，就像 Claude 在 Claude Code 里表现最好不是偶然。
  • 证伪方式也很直接：等社区拿 dsh 跑 DeepSeek 模型与跑别家模型的实测对比。目前没有任何公开 benchmark 支持或否定这一点。
为什么重要

「模型厂亲自开源 harness」这个行为本身，最大的价值可能不在工具，而在它公开了这家模型厂认为 agent 应该怎么被驱动——这是观察各家后训练思路的窗口。

4

推断 · 基于功能设计取向

dsh 的设计重心在长程任务：状态、隔离与自我延续

  • 把 dsh 超出别家的功能排在一起看——持久 PTY 终端、LSP、可持续对话的后台子代理、定时唤醒自己的 schedule、跨会话的 goal、可查历史的 session_query、防上下文膨胀的 spill 与 code mode——它们指向同一个问题域：让 agent 连续工作数小时而不失真。
  • 持久终端和 LSP 减少「一次性 shell + grep 猜测」带来的状态丢失；子代理隔离与 code mode 控制主上下文的污染；goal/schedule 解决跨会话的延续。
  • 需要说明：这些机制别家理论上都能以扩展形式补齐（Pi 的立场正是如此）；dsh 的差异在于把它们做成了默认配置且互相咬合（后台 bash、PTY、子代理统一由 job_* 三个工具收纳）。
为什么重要

这给出了评估 dsh 的正确姿势：别在「一问一答」任务上比（大家都一样），要在「连续跑两小时的脏活」上比——那才是这套设计要赢的地方。
